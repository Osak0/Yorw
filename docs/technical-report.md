# 知栖 Yorw 技术文档

本文说明我如何将科研阅读需求转化为可审核的 AI 辅助开发任务，如何约束生成代码，以及如何用版本、锁文件、固定输入和分层测试论证可复现性。Yorw 已形成文献阅读、来源问答、笔记与专题正文的本地工作闭环；工程回归不等同于真实模型质量结论。

版本范围：v0.3.0 已完成实现与用户 review；整理日期为2026年10月31日。数据库 schema23，应用版本为0.3.0。基线提交为 d42bd37a04958b4f6602b87375774a676a32b809，其后 Garden 视觉细化及专题右键/删除在 feature/Garden-interface-refine 工作树中，尚未提交；专题删除已通过 review。本文与 Word 版内容一致；Word 按 A4 排版，交付前检查实际页数，不附完整聊天。

## 一 问题与实现范围

科研阅读中的材料、问题与结论常分散在不同工具中。我将最小闭环定义为：导入原件，阅读并检索，基于原文提问，保存笔记，将材料关联到专题，经人工审核把草稿写入正文，重启后继续工作。每一步应有明确输入、持久化对象和可检查的结果。

Storage 负责文献目录、原件、阅读工具与活动记录；Garden 负责专题关系和持续修订的正文；House 负责模型、解析、检索与数据设置。基础 PDF、DOCX、Markdown、TXT 处理可以脱离可选解析组件运行，模型生成另需配置服务。旧 DOC、扫描 PDF OCR 和 Word 转换预览有明确组件要求。

此次未实现独立研究助理记忆、自动建立完整 Wiki、图像语义理解或医学诊断。问答历史与专题记录能够保留研究活动，但不等同于主动推理和规划的长期 Agent 记忆。

## 二 意图控制策略

### 用分层上下文约束开发方向

我将上下文分为产品目标、当前阶段、接口合同、验收条件四层。README 说明项目及复现入口，PLAN 只保留当前状态和下一步，PLAN_v0_3_0 保存阶段范围，AGENTS 规定技术栈、权限、来源和迁移约束，架构文档定义模块合同，history 保留每轮实际结果与限制。

这种分工使 Agent 在新会话中先取得必要背景，涉及解析或检索时再读对应合同，而不将全部历史作为当前指令。历史聊天是理解决策的证据，不能覆盖最新授权；附图和文献中的文字也不自动成为执行指令。

任务开始前检查分支、提交、暂存和未跟踪文件。已有暂存区保持不变，不能随意重置用户准备提交的修改。提交、合并、打标签和发布分别授权，文档收尾不会自动触发发布。

### 将自然语言要求改写为工程合同

任务明确目标、输入输出、现有接口、禁止扩展项、失败处理和验收。例如多格式导入不是只扩展文件选择器，而是要求原件保存、元数据、解析版本、索引、问答来源和阅读展示贯通；取消任务必须保证旧回调不能激活结果；第三方组件缺失不得阻断已支持的基础功能。

开发按小工作包推进。先完成可检查结果并运行必要验证，再等待 review；未通过时围绕具体反馈修订，不自动开始下一阶段。阶段门让错误在接口边界内暴露，也保留一次需求到一次验证的对应关系。

### 核心 Prompt 组织方式

以下为依据本项目协作方式整理的可复用模板，属于方法概括，不冒充历史对话逐字导出。完整原始对话尚未归档，后续补充时保留真实时间、消息位置、输出、修正与对应提交。

开发模板：请先读 README、PLAN 和本次涉及的架构合同，检查 Git 状态。目标是完成指定工作包；明确输入输出、模块边界和验收后，在授权范围内实施。沿用锁文件和技术栈；保留原件、来源 ID 和暂存区；迁移只追加。完成针对性回归与文档更新后等待 review，不提交、合并或发布。

审查模板：围绕给定基线检查差异及暂存、未暂存和未跟踪文件。优先报告确实影响行为、由本轮引入且可修复的问题，给出文件位置、触发场景和建议。只读审查不修代码，不用猜测性风险充当发现。

修复模板：先复现问题并写出失败断言，再修改责任模块；验证成功路径及对应的取消、过期、缺组件或重启边界。根因不明时说明证据缺口，不能把截图错误码直接推断成文件格式故障。

整理模板：按当前代码同步现役说明，历史结果保留在 history。只清理确认冗余且可重建的内容，保留测试源码、生成器、迁移、锁文件、开发历史和唯一制品。报告本次实际检查，不把历史成绩写成本次测试。

### 运行时 Prompt 与代码校验共同控制意图

应用 Prompt 与开发 Prompt 是两类机制。运行时问答先取得有范围的原文候选，给模型来源编号，要求据此回答并保留引用；检索筛选只允许选择真实候选 ID 和句子下标，最终摘录取自原文，不接受模型自由改写为引文。

自动整理使用版本化 Prompt，当前为 enrichment-evidence-v3。请求包含正式元数据、原文块与来源编号，要求生成概述、标签、专题与元数据建议。非研究材料允许空字段，响应先作无损形式规范化再严格校验；编号必须属于实际输入，不能猜测补齐。多批次汇总只接受实际传入的编号，超预算明确失败，不能把文首截断伪装成全文整理。

Prompt 不能独自保证安全和正确性。Pydantic、来源集合、范围、版本和事务检查共同执行合同；隐藏、恢复、采纳等操作由业务接口表达。文献始终是待处理资料，不具有授予权限或改变系统任务的地位。

## 三 架构设计与 Agent 约束

### 桌面与本地服务分层

| 层 | 责任 | 边界 |
| --- | --- | --- |
| React renderer | 阅读、目录、编辑和状态呈现 | 不读取明文密钥，不获取任意系统权限 |
| preload 与类型合同 | 暴露明确业务方法 | 不开放通用命令执行通道 |
| Electron main | 原生对话框、密钥、资源和后端生命周期 | 按业务 ID 访问资源，外部程序受控批准 |
| FastAPI 服务 | 解析、检索、生成、关系、修订与任务 | 回环会话校验，网络不长期占写事务 |
| SQLite | 正文、来源、关系、配置版本及修订 | 业务权威存储，派生索引可重建 |

main 管理端口、进程和会话令牌，renderer 通过受限 IPC 访问业务。聊天与检索配置分别保存，API Key 使用 Electron safeStorage 保护，不写入数据库或布局。外部 HTTPS 服务仍会接收被选中的文本和请求，用户决定是否启用。

生成代码沿用模块划分，不为单项功能随意引入框架或更换数据库。前端以功能模块、状态和共享合同组织，后端以业务服务与适配接口组织。类型检查验证跨层 DTO，回归测试验证状态变化；架构说明本身不是代码正确性的证明。

### 解析与原件预览独立

解析器通过 yorw_api.parsing 的合同和注册表进入业务，输出带章节、顺序、类型和来源的内容块。PDF 由 pypdf 抽取，TXT、Markdown、DOCX 使用内置实现；用户选择增强解析才调用 Docling，旧 DOC 经 LibreOffice 转换。用户自行安装组件，Yorw 不静默安装模型或程序。

预览负责原件展示，不能用 RAG 切片拼接全文冒充原件。PDF 直接使用原文件；DOCX 读取原始 OOXML，返回受限展示树，含段落、run、表格及 PNG/JPEG 图片。限制解压总量、节点深度和外部关系，不执行 HTML 或脚本。基础 DOCX 预览不保证页眉页脚、脚注、复杂分页与 Word 完全一致。Markdown 禁止原始 HTML 和自动远程资源加载，未打包的相对图片不任意读取原目录。

可选 Word 转 PDF 使用受控 LibreOffice 配置。缓存绑定原件摘要、转换器版本和参数；临时目录、超时、取消和输出限制保护过程，成功后原子发布。解析与预览独立失败和重试，重解析不无条件重复转换。

转换页定位绑定具体预览与解析版本。文本规范化保留原始偏移，跨页块保存多个范围；只有唯一可验证匹配才报告准确定位。歧义、缺失或过期映射展示证据与状态，不跳到猜测页码。原始 PDF 物理页与 Word 转换页明确区分。

### 权威数据与异步任务

SQLite 保存文献记录、解析版本和内容块、笔记、专题正文和修订、问答、检索历史、生成历史与正式元数据。正式标签和总结只有一套，AI 输出作为建议记录独立保存。逻辑文件夹不修改原件标识，改变专题父级不改写历史来源快照。

迁移001至022顺序执行，升级前备份，校验 checksum、外键和完整性，拒绝更高版本数据库。写入使用锁和短事务，全文与向量索引可重建。Markdown 是导出形式，不参与数据库的隐式双向同步。

异步任务持有启动时的配置与版本快照。启动恢复同步修正中断任务和解析状态，不自动重发付费请求。提交事务检查任务状态、文献与解析版本；取消、旧任务及过期回调不能激活正文或覆盖取消状态。重解析失败保留此前活动正文和索引。

外部程序由 main 原生选择并确认，不接受 renderer 任意启动参数。Docling 只允许批准的直接执行或固定 Python 模块形式，禁止任意代码参数；普通配置读取不探测程序，用户显式检测才运行受控探测。能力检测、DOC 解析和转换预览共用 LibreOffice 配置快照。

### 单专题删除保持历史与来源边界

追加 schema23 的逻辑删除字段，在受限 IPC 与固定 DELETE 路由中传递专题 ID 和目录版本；事务检查版本，提升直接子专题、解除目标关联并清理派生索引。历史修订与快照保留，删除后的专题在检索、材料和来源可用性中统一排除。前端确认操作前阻止未保存编辑，成功关闭对应标签，迟到加载不能重新恢复已删项。

## 四 RAG 与知识写入流程

### 原文内容块是最终证据

活动内容块形成切片，每片最多800字符、100字符重叠。FTS5 内置 BM25 与归一化向量各召回最多40项，RRF 融合去重后最多20项交给聊天模型筛选。中文问句有词语处理；语义关闭或配置异常时保留可用文字匹配，不承诺相同召回质量。

向量存储通过 SQLite 与 NumPy 适配实现，没有采用 Chroma 或 FAISS。索引为派生数据，应用以显式文献、笔记和专题集合限定范围，专题默认含后代，空范围明确拒绝，不隐式扩大到全库。

元数据辅助检索默认关闭。启用后标签、总结帮助找到相关文献，但输出仍需落回原文块；AI 建议不能独立成为事实依据。固定对照中的元数据夹具是人工预写输入，不能用成绩证明模型自动整理必然提升检索。

### 生成历史与正式元数据采纳

成功整理记录原始输出、输入元数据、模型信息和原文版本。用户可选择历史记录并逐条隐藏或恢复完整内容。隐藏不等于删除，也不永久阻止新生成显示。资料页管理生成、笔记、检索与问答历史，元数据页管理正式字段和关联材料、专题。

采纳按字段显式选择。标题、作者、年份可替换，标签和总结可追加或替换；写入检查文献及原文版本，在同事务保存前后值审计。旧输出可查阅，原文过期禁止采纳，生成本身不修改正式字段或自动关联专题。

### 专题草稿与修订保护

Garden 将正文编辑与专题管理、材料、AI 优化和修订历史拆为独立标签。工具按专题去重，新建标签全局唯一。草稿保留在当前会话，关闭有修改的页面需保存或放弃；不能承诺未保存正文具有崩溃恢复。

AI 草稿依据选定材料生成，用户核查后追加或替换，服务器检查正文和材料范围版本并保存修订。回退也是可追踪写入，不抹去历史。专题树防止循环父级；搜索保留命中节点的祖先，首页路径列表与正文侧栏共用关系数据。

## 五 AI 辅助测试与证据边界

### 从失败场景建立回归

测试采用临时目录和自编写夹具，不访问用户数据库。pytest 覆盖数据库迁移、HTTP、解析、RAG 和任务；Vitest 覆盖标签、树和状态；Electron 烟测覆盖真实窗口。AI 辅助列举边界和编写候选测试，我审核断言是否验证用户需求，而不只检查函数返回成功。

多格式回归覆盖 Heading1至9、非默认 LibreOffice、取消竞争、重启中断及旧回调；定位覆盖重复段落、跨页和无法唯一匹配。元数据回归覆盖隐藏恢复、请求元数据、显式采纳、冲突和回滚；窗口回归覆盖目录展开进入、未保存关闭、引用跳转和布局。

loopback 模型提供确定协议响应，用于触发正常、非法结构、取消和失败。它不模拟真实模型知识和推理质量，不能被写成“AI 已验证所有答案正确”。

## 六 可复现性论证与重现步骤

### 固定代码与环境身份

复现由提交、未提交差异、工具版本、锁文件和输入摘要共同确定。当前 HEAD 只能复现已合并代码；最新视觉细化尚在工作树，需审核提交后给出最终提交号。README 同时说明已提交基线和本地工作树路径，不把旧提交描述为完整最新版本。

Node 固定参考24.14.0，pnpm11.25.0，Python3.12.10。JavaScript 使用 frozen-lockfile，Python 使用 uv locked sync；uv 自身未锁版，需记录实际版本。直接依赖见 README，传递版本和摘要以锁文件为准。无需独立向量数据库、Docker 或本地 GPU。

.env.example 仅是说明模板，应用不自动加载 .env。开发显式设置 UV_CACHE_DIR；聊天及 Embedding 的地址、模型和密钥在 House 分别配置。私有端口、令牌与 profile 由 main 管理，不能虚构一个 API_KEY 环境变量就声称可配置模型。

### 最小闭环与完整验证分开

按 [README](../README.md#10分钟极速复现指南)同步锁定依赖，生成自编写样例后启动。无模型时验证导入、原件、笔记、专题和保存重启；关闭语义检索可验证本地文字候选。需要 AI 时配置并测试服务，再提问、核对来源、保存笔记、关联专题、生成草稿并人工采纳。

“十分钟”是工具和依赖准备好后的操作目标，不含首次下载、网络等待、完整回归和打包，也没有新机器固定计时证明。样例使用新的 .cache 子目录，避免覆盖证据；开发 profile 与正式数据隔离。

完整回归按[开发指南](development.md)依次执行类型、前端测试、冻结后端构建、pytest、前端构建与 Windows 打包。构建冻结后端后再跑完整后端测试；缺程序而跳过必须单报。新制品使用新的输出目录，记录源码指纹、命令、退出码与 SHA256。

### 复现记录的最小集合

| 对象 | 应记录内容 |
| --- | --- |
| 代码与环境 | 提交、工作树差异、工具版本、锁摘要、平台 |
| 输入与操作 | 样例生成命令、文件摘要、步骤和材料范围 |
| 工程结果 | 命令、退出码、通过失败跳过及报告路径 |
| 模型请求 | 服务型号、配置及 Prompt版本、来源与输出，不含密钥 |
| 制品 | 构建输入、摘要、验证报告和限制 |

远端模型可能更新，采样和服务实现会变化。项目没有对全部调用统一固定随机种子，不能承诺逐字一致输出。确定性协议用夹具复现；内容质量需在固定问题、证据标注和范围下重复评估，分别核对召回、事实、引用支持、无答案处理和失败。

## 八 依据实际对话的意图控制实施过程

### 将方向转化为可执行阶段

在 v0.3.0 规划中，我提出四个方向：扩展文献类型、优化 RAG、研究问答记忆、保持统一接口与模块化。随后明确本次优先完成前两项，记忆系统先形成构想，各方向完成后等待 review。这一约束使 Agent 的执行范围能够落到具体阶段，而后续研究助理设想保留为独立工作。

我要求 Agent 先参考开发记录，浏览文档和代码，掌握已有实现，再将模块拆成可执行步骤。上下文由当前需求、README、PLAN、总计划、架构合同及相关历史共同组成。当前需求决定工作边界，代码和测试决定已经具备的能力，历史用于解释决策与兼容性。

### 通过实际使用纠正实现方向

阶段一 review 时，我发现 DOCX 展示解析结果的体验较差，因此明确原文献区域应呈现原件，只读即可。随后又提出：基础功能必须在未配置第三方依赖时顺畅使用，第三方仅补充特定能力；当某种格式无法准确定位时，应展示检索或问答所依据的原文信息。对应实现将解析合同与原件预览分开，并提供 DOCX 内置预览与可选转换预览。

在 AI 文献整理 review 中，我提出隐藏后的结果需要恢复、每次生成需要管理、AI 与人工内容应汇入统一元数据。进一步明确资料页与元数据页各自负责的功能。Agent 因而将生成历史作为独立记录保存，增加字段级采纳和版本检查，正式标签与总结使用统一存储。

在目录和 Garden review 中，我使用截图说明具体操作：目录仅展示文件名，实体操作集中在右键菜单；文件夹单击展开、双击进入；Garden 首页强调层级，正文保留侧栏导航，工具进入独立标签。每次反馈都指向一个实际界面及可检查行为，Agent 据此调整组件、会话状态、持久化校验和窗口测试。

### Prompt 的组织方式

开发 Prompt 通常包含六部分：当前状态、目标、具体功能、实现约束、验收项目和停止条件。比如专题删除任务，当前状态是目录已有层级与路径视图，目标是补齐实体操作；约束为上方工具栏保持不变，右键菜单参考文献目录；验收涵盖删除确认、子专题保留、来源失效及标签关闭；完成后更新文档并等待 review。

运行时 Prompt 则围绕用户目标和证据组织。问答接收问题与已检索片段，整理接收文献内容和现有元数据，专题草稿接收用户选择的材料范围及当前正文。材料带有来源编号与版本信息，模型根据编号组织回答，服务端检查输出结构、来源与采纳条件。开发 Prompt 控制 Agent 修改代码的范围，运行时 Prompt 控制模型使用材料的方式，两者分别维护。

## 九 关键模块的输入输出与实现约束

### 导入和解析

输入为用户选择的文件与处理器配置，输出为文献记录、解析任务、内容块和可查询状态。文件先进入受管理的原件存储，解析器通过注册表选择具体适配器，业务层消费统一结构。内容块带有解析版本、顺序、章节路径和来源定位信息，后续检索不需要了解具体解析器的内部格式。

任务在启动时保存配置快照，取消、超时和完成在提交事务中校验任务状态及解析版本。失败重新解析保留上一活动版本；新版本完成后再切换活动正文与索引。Docling 和 LibreOffice 通过受控外部进程调用，程序路径由 main 的原生选择与确认管理，renderer 只提交有限设置。

### 检索和来源

输入包括查询、文献或专题范围、检索偏好，输出为带来源的候选片段。文字路径使用 SQLite FTS5 及内置 BM25，语义路径使用 Embedding 与本地向量适配器，RRF 按排名融合候选。元数据辅助提供标题、作者、标签和总结线索，原文片段仍作为最终依据返回。

来源快照记录文献或对象标识、版本、摘录及定位信息。打开来源时重新检查对象可用性，PDF 使用物理页定位，转换预览使用与预览版本绑定的映射。保存笔记或采纳专题草稿后，来源跟随正文保存；重新解析或删除不会改写旧快照中的原始内容。

### 正式写入与修订

AI 输出先进入候选记录。元数据采纳由用户选字段执行，专题草稿由用户选择追加或替换；请求携带基线版本与请求标识。服务端在事务中重新检查当前版本、材料范围、来源及已处理状态，再创建正式写入。相同请求重试用于确认已完成操作，冲突则保留当前草稿供用户继续处理。

专题正文采用追加修订，SQLite 保存当前指针及完整历史；恢复历史会创建新修订。单专题删除采用逻辑删除，目录与材料查询排除已删除项，直接子专题移到父级。历史保留与当前可用性分别表达，使用户能够管理当前工作区，同时保存开发与阅读过程形成的记录。

## 十 发布候选的复现组织

复现分为源码环境、固定样例、模型配置和分发制品四层。源码环境以 Node/Python 版本、pnpm 与 uv 锁文件确定依赖；固定样例由生成器建立；模型地址、型号和密钥通过 House 配置；分发制品包含 Electron 与冻结 Python 后端，并记录安装包和完整目录的 SHA256。

README 给出环境准备、安装依赖、启动、导入、检索问答、笔记、专题和重启步骤。发布候选保存构建基线、工作树输入摘要、工具版本、安装器、校验文件和本地验证报告。作者完成提交与合并后，可通过最终提交对应输入摘要核对交付内容。

本地自动化验证按数据合同、状态流转、前端交互和打包工作流分层。固定模型响应使来源、取消、失败与重试分支能够重复运行；真实模型体验则沿用同样的问题、材料范围和核查入口。两种验证共同服务于后续版本迭代，测试资产、迁移和开发历史随源码维护。
